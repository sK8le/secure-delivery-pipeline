# Допуск по пользователю контейнерного образа

Защищённый конвейер после docker build и до сохранения образа выполняет
scripts/check_image_user.py. Проверка читает Config.User собранного образа
через docker image inspect. Приложение при этом не запускается.

Политика требует явно заданный числовой UID от 1 до 4294967294.
Допускается UID:GID, где GID также числовой, включая 0. Имена пользователей
не разрешаются: их UID эта проверка не определяет. Текущий USER 10001 проходит.
Пустой, отсутствующий или нулевой пользователь блокирует допуск. Для отсутствующего
поля используется безопасное чтение объекта Config, а не шаблон .Config.User.

Результат image-user-check.json сохраняется отдельным артефактом даже при отказе.
Код 0 — допуск; 1 — нарушение политики; 2 — ошибка инспекции или её формата.
Оба отказа останавливают сохранение образа и зависимые стадии, но ошибка
инфраструктуры не считается обнаруженной уязвимостью в экспериментальной матрице.
Baseline этой проверки не выполняет.

Это проверка настройки пользователя образа по умолчанию. Она не измеряет UID
приложения, не доказывает отсутствие эскалации привилегий и не заменяет
runAsNonRoot/runAsUser в Kubernetes.

Исходный E11 (PR8) прошёл оба конвейера при удалённом USER. Этот отрицательный
результат сохраняется. После внедрения контроля требуется отдельный повтор того
же удаления с неизменёнными тестами и политикой: clean должен пройти, мутант —
блокироваться именно этим шагом. До фактических прогонов это критерий приёмки,
а не установленный результат.
