# Методика сравнения конвейеров

## Статус и границы

Это план воспроизводимых испытаний, а не готовые результаты. Реальная поставка защищённого варианта уже реализована. Baseline в текущей редакции заканчивается сохранением образа; он ещё не измеряет полную поставку на ВМ. Его прежний шаг echo удалён, поскольку не подтверждал развёртывание.

Исторические результаты E1–E11 относятся к исходной версии проекта. Они сохраняются отдельно и не выдаются за прогоны новой версии. E — внутренний идентификатор эксперимента, а не номер категории OWASP. Сопоставление с категориями выполняется отдельно для каждого реального дефекта.

## Что сравнивается

Оба варианта используют один коммит приложения, Dockerfile, версии Python и ОС runner, положительные пользовательские сценарии из tests/functional и тесты запуска БД из tests/test_database.py. Оба устанавливают одни и те же requirements.txt и requirements-dev.txt; наличие установленного сканера само по себе не считается запуском контроля. В защищённом варианте общий набор входит в pytest tests/ вместе с регрессионными тестами безопасности.

| Свойство | Baseline CI | Защищённый конвейер |
|---|---|---|
| Обычные функции приложения и запуск БД | Общий набор | Тот же общий набор |
| Злоумышленные входные данные, изоляция команд, политика допуска | Не проверяются | Регрессионные тесты |
| Секреты, код, зависимости | Не сканируются | Gitleaks, Bandit, Semgrep, pip-audit, Trivy |
| Образ и работающее приложение | Сборка и сохранение образа | Сканирование образа, HTTP-проверки, ZAP |
| Реальное обновление ВМ | Ещё не реализовано для сравнения | Публикация точного образа и локальная служба доставки |

Положительный функциональный набор проверяет доступность форм и healthz, регистрацию/вход/выход, импорт с последующим просмотром и поиском собственной записи, расчёт CVSS по корректному вектору. Он не проверяет запрет чужого доступа, флаги cookie, экранирование или опасные выражения. Регрессии этих защит остаются в защищённом наборе.

## Испытания обнаружения

1. Зафиксировать исходный SHA, окружение и версии инструментов. Чистая версия должна пройти оба CI-варианта.
2. Для каждого случая создать отдельную экспериментальную ветку с одним контролируемым изменением. Сохранить diff и фактический SHA проверки, включая merge SHA GitHub Actions.
3. Отдельно подтвердить наличие дефекта. Например, для нарушения доступа — успешное чтение заранее созданной чужой записи; для опасного eval — изменение нужного выражения и безопасная контрольная демонстрация. Упавшая установка зависимости не подтверждает обнаружение дефекта.
4. На одном и том же состоянии кода запустить оба варианта. Уязвимые изменения исследуются в одноразовых окружениях CI; в main и на рабочую ВМ они не сливаются.
5. Записать конкретный контроль, находку/провал утверждения, статус блокировки и фактическое выполнение последующих этапов. Общий красный статус без причины недостаточен.

Для каждого случая записываются: идентификатор, дефект, diff/SHA, проверка наличия, ожидаемый контроль, находка или пропуск, ошибка инфраструктуры при наличии, допуск/блокировка, ссылки на оба запуска и исходные отчёты.

Полнота обнаружения — доля подтверждённых внесённых дефектов, обнаруженных заявленным набором контролей. Блокировка учитывается отдельно. Неоднозначные случаи и инфраструктурные ошибки выделяются и повторяются; они не засчитываются ни как обнаружение, ни как честный пропуск. Предварительно задаются состав набора и правила учёта, чтобы не подбирать знаменатель после результатов. Число тестов pytest и число утверждений HTTP-сценария не являются числом дефектов.

E11 (удалённый USER образа) требует отдельной трактовки: Kubernetes может продолжать запуск с runAsUser=10001. Настройка образа и фактический UID процесса — разные свойства; отсутствие проверки первого нельзя описывать как доказанный root-процесс в кластере.

## Измерение времени

Исторические прогоны с echo и текущий baseline до сохранения образа не используются как время непрерывной поставки. Для CI отдельно допустимо измерять время до готового артефакта, явно называя эту границу.

Перед серией полной поставки нужно реализовать одинаковый механизм развёртывания чистой контрольной версии в обоих вариантах в отдельном экспериментальном пространстве имён. Рабочая среда и её защита main сохраняются. Уязвимые версии для серии времени не требуются. До реализации и приёмки этого механизма замеры полной поставки не начинаются.

Затем выполнить не менее пяти сопоставимых пар, чередуя порядок baseline/secured. Сохранить исходные UTC-времена: фиксация/постановка запуска, начало выполнения, готовность образа, публикация, начало применения на ВМ, готовность всех реплик и проверка приложения. Отдельно учесть очередь GitHub, интервал таймера, скачивание и кэш; не вычитать их молча. Фиксировать runner, ресурсы ВМ, число реплик, базовый образ по digest, версии Python-пакетов и сканеров/их баз, условия кэша и изменения внешних источников.

Для каждой пары считать абсолютную разницу и относительные накладные расходы: (T_secured - T_baseline) / T_baseline × 100%. Показать исходные значения и разброс; формулировать выводы только для измеренной конфигурации.

## Обнаружение атаки в эксплуатации

Отдельная серия не менее пяти повторов: известное начало учебной атаки на собственный стенд, время перехода Prometheus alert в firing и, если измеряется, время получения уведомления. Эти события не подменяют друг друга. Перед повтором проверяются восстановление нормального состояния и отсутствие уже активного alert. Нужны синхронизированные часы, одинаковый профиль нагрузки и исходные отчёты.

## Скриншоты и исходные данные

О нужном снимке сообщается до запуска. Минимальный комплект: исходная версия/идентификатор опыта, конкретная находка и блокировка защищённого варианта, успешный baseline на том же дефекте, обе готовые реплики с идентификатором доставленного образа для серии поставки, временные отметки атаки и firing для мониторинга. Снимки дополняют XML/JSON и журналы, а не заменяют их. Неуспешные попытки сохраняются с объяснением и не стираются успешным повтором.
